# Этап 6: внешний ревьюер

Свежий агент без контекста задачи видит дифф так, как его увидит ревьюер MR, а не автор. Поэтому
каждая итерация — **новый** агент, не форк и не продолжение прошлого. Пока он работает, дифф не трогать.

## Запуск

В треде bb (задан `$BB_THREAD_ID`) ревьюер — дочерний тред в том же окружении: так он доступен
любому провайдеру. Промпт — в файл во временном каталоге сессии, затем:

```bash
id=$(bb thread spawn --parent-self --lifecycle-owner-thread "$BB_THREAD_ID" \
  --environment "$BB_ENVIRONMENT_ID" --title "mr-cycle: внешнее ревью <N>" \
  --prompt-file <файл> --json | jq -r .id)
bb thread wait "$id" --timeout 9m   # вышел по таймауту — повторить
bb thread output "$id"
```

Провайдер и модель — какие назвал владелец (`--provider`, `--model`), иначе — по умолчанию проекта.

Вне bb — субагент `claude-reviewer`, если такой тип есть, иначе `general-purpose`.

## Промпт

```
Сделай независимое код-ревью изменений ветки в git worktree <путь>.
Каталоги планов и спек не смотри. Дифф: `git -C <путь> diff <merge-base>` (сгенерированное и моки
пропусти); новые файлы: <список>.
Ищи по всем пунктам, по убыванию важности: баги; переусложнение — хелперы, типы и конструкторы с
одним вызовом, обёртки над готовым, новые методы зависимостей при уже имеющихся, хитрый код вместо
прямого; расхождения со стилем и архитектурой соседних файлов, включая приёмы в тестах, которых у
соседей нет; тесты, которые не проверяют заявленное в имени, проверяют по логам, проходят при любом
коде, дублируют другой уровень; тесты, которых нет: функция, объявленная или изменённая MR, без теста,
который вызывает её саму (тест вызывающего не считается), и ветка, которую ни один тест не включает,
в том числе параметром (размер чанка, лимит) — кандидатов покажет
`bash <каталог скилла>/scripts/pyramid.sh` в корне worktree; неточные комментарии и
комментарии-пересказы.
<Семантика, без которой ревьюер ошибётся, — 1–2 строки.>
Уже рассмотрено и отклонено — не поднимай повторно: <пункт — причина>.
Каждую находку проверь по коду. Формат: файл:строка, серьёзность (bug/risk/simplify/style/test/comment),
что не так и сценарий, предлагаемое исправление. Нет находок — так и напиши.
```

## Разбор находок

Каждая находка — два фильтра:
1. **Правдива ли?** Проверить по коду и семантике, не по памяти. Ложную отклонить с объяснением.
2. **Нужна ли?** Что будет, если не делать. Решение плана или спеки — отклонить со ссылкой.
   Стилевую принимать, если код расходится с соседями или правилами проекта; вкусовую отклонять.

Принятое исправить и прогнать проверки. Отклонённое с причиной — в список «не поднимай» следующей
итерации; после последней — в итоговый отчёт и в файл заметок снимка.

## Сколько итераций

Две-три: третью запускать, если после второй ещё было что исправлять. На третьей цикл
заканчивается: её находки разобрать и исправить, а в отчёте указать, какие правки внешний ревьюер
не видел.

Если владелец просит закончить раньше, его слово важнее: находки текущей итерации всё равно
разобрать, принятое исправить и прогнать финальные проверки, а в отчёте указать, сколько итераций
пройдено.
