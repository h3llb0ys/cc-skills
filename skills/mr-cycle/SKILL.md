# MR cycle

Код MR пишется целиком и без коммита, потом полируется восемью этапами — **каждый отдельным
проходом по диффу с коротким отчётом**. В одном общем проходе ревью вытесняет упрощение, тесты
не сверяются с пирамидой, а комментарии правятся раньше, чем устоялся код; отдельные проходы
ловят то, что общий пропускает.

## Режимы

| Ситуация | Что делать |
|---|---|
| Команда на код MR | прочитать документ плана MR и спеку (по ссылкам из запроса и плана; спеки нет — работать по плану), этап 0, затем этапы 1–8 |
| Владелец поправил дифф после цикла и просит ревью или правки | прочитать `rerun.md`: полный цикл заново |
| В дереве правки, не относящиеся к MR (документы плана и спеки к ним не относятся) | спросить до начала работы |
| По документу работать невозможно | спросить |

## Правила

- **Не коммитить и не пушить** — владелец смотрит и коммитит сам.
- Это исполнение согласованного плана: процессные скиллы с согласованием дизайна не запускать.
- Этапы цикла — не этапы плана: весь MR — один этап плана. Этапы цикла идут подряд, без пауз;
  свой план реализации пишешь в чат и ответа не ждёшь. Останавливаешься только на вопросах
  из «Режимов» и на итоговом отчёте.
- Перед стартом заново `git status` и `git log` — снимок из начала сессии устаревает. Если upstream
  ветки — main, снять: `git branch --unset-upstream`.
- Дифф MR — от merge-base с main: закоммиченное в ветке, незакоммиченное и новые файлы. Владелец
  коммитит по ходу, закоммиченное — тоже часть MR и проходит все этапы.
- Документы плана и спеки только читать; где документ расходится с соседями, главнее документ.
  Расхождение документа с кодом — сразу в чат, работа идёт по документу.
- Не переоткрывать решения из плана, спеки, памяти проекта и отклонённое на прошлых итерациях.
- Инструкции проекта — CLAUDE.md или AGENTS.md; память проекта — если провайдер её ведёт.
  Временный каталог сессии — scratchpad провайдера, в bb — `$BB_THREAD_STORAGE`.
- Проверки (команды — из инструкций и памяти проекта): после этапа, менявшего файлы, — сборка, vet
  с тегами, линт, юнит-тесты затронутых пакетов; интеграционные наборы, покрывающие изменённый
  код, — после этапов 0 и 4, после правки SQL или фикстур и после последней правки цикла.
- Язык и формат комментариев — по инструкциям и памяти проекта.
- Вызов цикла — явное разрешение на агентов этапа 6.
- В треде bb (задан `$BB_THREAD_ID`) до этапа 0 прочитать `bb.md`: ход цикла отмечается
  в интерфейсе bb.

## Этапы

| № | Этап | Готово, когда |
|---|---|---|
| 0 | Код файл за файлом по образцу 2–3 соседних пакетов того же слоя, юнит-тесты на новые ветки, генерация штатным генератором | всё зелёное, в диффе генерации только ожидаемое |
| 1 | Ревью: баги, null и пустые значения, границы, совместимость контракта, ошибка без частичного результата, неточные комментарии | каждое замечание проверено по коду и исправлено |
| 2 | Упрощение. `bash <каталог скилла>/scripts/inventory.sh` в корне репозитория; по каждой строке разделов «used once», «Interface methods», «New files» — вердикт: встроить, убрать или оставить. Оставить можно, только если встраивание вкладывает ветвления в цикл вызывающего или так требует документ; последовательный шаг (чтение перед циклом, обработчик в `httptest.NewServer`) встраивается и на 30 строк. «Был до MR» и «у него свои тесты» — не причины: MR его тронул, а тест переезжает на вызывающего. Раздел «log.FromCtx where the package has its own logger helper» — логгер как в соседних методах. Сверх списка: тип или конструктор, который лишь оборачивает готовое (конфиг, конструктор сущности); хитрый код там, где хватает прямого; новый метод зависимости, когда уже есть общий (фильтр с IDs); дубли — по шаблону соседей; таблицы соответствий, которые план держит явными, не выводить из соглашения об именах | у каждой строки инвентаря вердикт, убрать нечего без потери смысла |
| 3 | Стиль и архитектура против соседей того же слоя: раскладка по файлам (одно действие юзкейса — один файл, его хелперы — в нём же), имена, логи тем же способом, что соседние методы пакета (общий хелпер логгера, если есть), ошибки, импорты, длина строк, место типов и proto-сообщений. Раздел инвентаря «External package members»: каждый приём — способом соседей или с причиной из документа | расхождений с соседями нет |
| 4 | Интеграционные кейсы в набор проекта (каталог — из запроса, инструкций или памяти проекта): чем больше разных кейсов, тем проще потом рефакторить. На каждое новое поведение — сквозной кейс в каждом харнессе набора, где оно проверяется, плюс сценарии смысла: оси, окна, роли, изоляция, пустые значения, сочетания | фикстуры дают ненулевые значения, кейсы лежат в группах, которые запускает CI, прогон с `-v` показывает их выполнение; README набора обновлён, если он описывает фикстуры |
| 5 | Повторное ревью и исправление — как этап 1, свежим взглядом по всему диффу, и заново инвентарь: в нём осталось только оставленное с причиной | каждое замечание проверено по коду и исправлено, имена тестов совпадают с проверками, всё зелёное |
| 6 | Внешний ревьюер без контекста — прочитать `reviewer.md` | по `reviewer.md` |
| 7 | Пирамида тестов — раздел «Этап 7» ниже | у каждой строки `pyramid.sh` вердикт, каждая мутация поймана, верхних дублей и проверок по логам нет |
| 8 | Комментарии: все добавленные (раздел «Comments» инвентаря плюс proto и SQL) — сократить, оставить причины и неочевидную семантику; doc-комментарий, который пересказывает имя, — удалить; правка doc-комментария proto — перегенерировать | по каждой строке вердикт, ни один не врёт и не пересказывает код |

Пирамида и комментарии идут последними: ревью этапов 1–6 меняют рабочий код, а тесты и комментарии
сверяются с кодом, который больше не меняется. Если этап 7 или 8 поменял рабочий код — этап 7 заново.

### Этап 7: пирамида тестов

Два прохода и мутация, в этом порядке. Верхние дубли — только второй проход: без первого пропущенные
тесты нижних функций не видны.

1. **Снизу.** `bash <каталог скилла>/scripts/pyramid.sh [флаги go test, как у юнит-тестов проекта]`
   в корне репозитория; по каждой строке — вердикт.
   - «without a direct test call»: тест, который вызывает саму функцию, на все её ветки и краевые
     значения. Тест вызывающего не считается, даже если вызывающий — тонкая склейка. Функция попала
     в список из-за соседнего hunk'а, а её тело не менялось — вердикт «тело не менялось».
   - «no test runs»: тест или причина, почему ветка недостижима.
   - Ветку, которую включает параметр (размер чанка, лимит, параллельность), тест включает этим
     параметром: размер чанка 1 и два ref, а не значение по умолчанию.
2. **Сверху.** Вопрос к каждому верхнему тесту: «какую ветку ЭТОЙ функции он ловит сверх нижнего?»
   Ответа нет — кейс уходит вниз (если там его нет) или удаляется. Кейс, который план требует
   наверху, — тоже вниз, с сообщением. Поведение проверяют результатом и вызовами моков: захват логов
   (раздел «Log capture» инвентаря) убрать, исход, видный только в логе, не проверять. Проверку,
   которая проходит при любом коде (поле или статус, которые тестируемый код не пишет) или повторяет
   проверку другого теста пакета, — удалить. Аргумент мока — точное значение; частично случайный —
   `gomock.Any()` и `DoAndReturn` с require, без `gomock.Cond`.
3. **Мутация.** Каждую новую ветку, от которой зависит результат (условие, ранний выход, граница,
   порядок обёрток), временно сломать и прогнать тест её функции: тест не упал — он ветку не
   проверяет, дописать. Файл перед мутацией копировать во временный каталог сессии и возвращать
   копией: дифф не закоммичен, `git checkout` и `git stash` его потеряют. После отката — прогнать
   пакет.

## Итоговый отчёт

Сначала снимок для повторного прогона: отклонённое с причинами — в файл во временном каталоге
сессии, затем в корне репозитория `bash <каталог скилла>/scripts/snapshot.sh save <файл>`. Скрипт
копирует изменённые и новые файлы в `~/.claude/mr-cycle/`; репозиторий он не меняет.

Отчёт: по этапам — что сделано и исправлено; находки внешних ревьюеров — принятые и отклонённые с
причинами; отступления от плана и от скилла; какие проверки зелёные и что не запускалось; что
вынести в описание MR; путь снимка. Последние слова — «ничего не закоммичено».

## Красные флаги

| Мысль | На деле |
|---|---|
| «Просили только ревью» — после того как владелец поправил дифф | Прочитать `rerun.md`: полный цикл заново |
| «Этапы похожи, пройду всё за раз» | Каждый этап — отдельный проход и отчёт |
| «Хелпер содержательный, не обёртка — оставлю» | Один вызов — встроить, если читается; «оставить» — с причиной в отчёте |
| «Хелпер был до MR / у него свои тесты» | MR его тронул — встроить, тесты перенести на вызывающего |
| «30 строк — встроенное хуже читается» | Последовательный шаг встраивается; оставлять — только если ветвления лягут в цикл |
| «Добавлю тест на поля лога» | Логи не тестируют: результат и вызовы моков |
| «Это закоммичено, не моё» | Закоммиченное в ветке — часть MR |
| «План требует этот тест» | Пирамида важнее плана: перенести вниз и сообщить |
| «Ветки покрыты тестом вызывающего» | Прямой тест вызывает саму функцию; через вызывающего не считается |
| «Верхних дублей нет — пирамида готова» | Это второй проход; первый — строки `pyramid.sh` с вердиктами |
| «В проде параметр по умолчанию, ветка не срабатывает» | Тест задаёт параметр так, чтобы ветка сработала |
| «Ревьюеры ничего не нашли про тесты» | Отсутствующий тест в диффе не виден: `pyramid.sh` и мутация, а не чужое молчание |
| «Ревьюер прав» или «помню, что это не так» | Проверить по коду, а не по памяти |
| «Тот же агент быстрее» | Каждая итерация — новый агент |
| «Всё зелёное — можно закоммитить» | Коммитит владелец |
