# Commit split

Предложить разбиение изменений на коммиты. Только текст в чате: `git add`, `git commit`,
`git stash` не выполнять — коммитит владелец.

## Что разбивать

- По умолчанию — всё незакоммиченное: `git status --short`, `git diff --stat`, новые файлы целиком.
  Если владелец назвал диапазон или ветку — его.
- Перед ответом заново проверить `git status --short` и `git log --oneline -5`: часть изменений
  могла уже уйти в коммиты, а файлы — поменяться владельцем.
- Не относящееся к работе (неотслеживаемые `docs/`, scratch, локальные конфиги) в коммиты
  не включать; перечислить отдельной строкой «не входит».

## Правила разбиения

- **Атомарность важнее согласованности.** Коммит — одно законченное по смыслу изменение.
  Он не обязан собираться и проходить тесты сам по себе.
- **Один файл — ровно в одном коммите.** Файл по коммитам не дробить, даже если в нём
  изменения разного смысла: класть туда, где его главный смысл.
- Сгенерированное — в коммит своего источника (proto + `gen/`, интерфейс + моки).
- Юнит-тесты — в коммит кода, который они проверяют (`x.go` + `x_test.go`).
- Фикстуры и SQL-данные — отдельным коммитом; сквозные/интеграционные тесты — отдельными
  коммитами по харнессу или смыслу, а не вперемешку с кодом.
- Документация набора (README тестов и т. п.) — к коммиту, который она описывает; если
  описывает несколько — в последний из них и сказать, куда её можно перенести.
- Порядок: контракт (proto/API) → каталог и доменные типы → хранилище → usecase/маппинг →
  потребитель (движок, транспорт) → фикстуры → интеграционные тесты → документация.
- Не плодить коммиты ради количества: 2–3 файла одного смысла — один коммит.

## Заголовок

- Префикс задачи из имени ветки: `feature/PROJ-123-…` → `PROJ-123: …`.
- По-английски, с маленькой буквы после префикса, повелительное наклонение, без точки,
  до ~72 символов: `PROJ-123: map device data from the stored row`.
- Без строк про генерацию Claude и Co-Authored-By.

## Перед ответом

- Сгенерированный код соответствует источнику: если источник (proto, интерфейс) правили после
  генерации — сказать, что перед коммитом нужно перегенерировать.
- Каждый изменённый и новый файл попал ровно в один коммит или в «не входит».

## Формат ответа

Нумерованный список, по пункту на коммит:

1. **`PROJ-123: <title>`**
   - `path/to/file.go`
   - `path/to/file_test.go`

   Что обеспечивает — одно-два предложения: какое поведение или контракт появляется.

В конце — «не входит» (если есть) и спорные места размещения одной строкой каждое.
Закончить напоминанием, что ничего не закоммичено.
