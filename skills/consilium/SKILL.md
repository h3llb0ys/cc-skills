# Consilium

## Overview

Совет консольных агентов для внешнего ревью: codex CLI (GPT), Claude-сабагенты (opus), cursor-agent (grok).
Два верхнеуровневых режима: **ревью артефакта** (код-ревью git-изменений; документы —
архитектурные решения, планы, спеки) и **выработка решения** (дизайн-совет, `references/design.md`).
Мультимодельные надстройки — по запросу, см. «Мультимодельные режимы».
Codex запускается только неинтерактивно (`codex exec`) и только на чтение — он рецензент, а не исполнитель.
Codex сам читает `AGENTS.md` репозитория — это осознанно. `--ignore-rules` отключает execpolicy
`.rules` (к `AGENTS.md` отношения не имеет) — тоже не добавляй.
Read-only = санбокс блокирует запись через shell-команды модели; свои state-файлы сессии codex пишет всё равно.

## Выбор модели

Модель и усилие — **раздельные** параметры: `-m <слаг>` и `-c model_reasoning_effort=<effort>`.
Слитный слаг вида `-m sol-high` невалиден: парсер его пропустит, но вызов упадёт на API.
Пользователь называет модель коротко («tera-medium», «luna») → разверни по таблице: слаг + effort из суффикса.

| Псевдоним | Слаг для `-m` | Efforts | Что за модель |
|---|---|---|---|
| sol | `gpt-5.6-sol` | low/medium/high/xhigh/max/ultra | флагман для агентного кодинга |
| tera, terra | `gpt-5.6-terra` | low/medium/high/xhigh/max/ultra | сбалансированная повседневная |
| luna | `gpt-5.6-luna` | low/medium/high/xhigh/max | быстрая и дешёвая |
| 5.5 | `gpt-5.5` | low/medium/high/xhigh | frontier: код + ресёрч |
| 5.4 | `gpt-5.4` | low/medium/high/xhigh | крепкая повседневная |
| mini | `gpt-5.4-mini` | low/medium/high/xhigh | маленькая, для простых задач |

- Модель не указана → `-m gpt-5.6-sol -c model_reasoning_effort=high`.
- Effort не указан → high. Это политика скилла (осознанный компромисс цена/качество).
  Неявный дефолт берётся из `~/.codex/config.toml` пользователя и может быть любым —
  поэтому `-m` и `-c model_reasoning_effort` задавай всегда явно.
- Незнакомое имя или слаг вне таблицы → сверься с каталогом; сырой вывод ~300 КБ, фильтруй:
  `codex debug models | python3 -c "import json,sys; [print(m['slug'], [e['effort'] for e in m['supported_reasoning_levels']]) for m in json.load(sys.stdin)['models'] if m['visibility']=='list']"`

Ниже `$MODEL` = `-m gpt-5.6-sol -c model_reasoning_effort=high` (или выбор пользователя).

## Промпт для участников

Собирай из пяти частей (для любого участника — codex, opus, grok):

1. Стандартная структура из рецептов ниже: роль, фокус, формат ответа. Плюс язык: «отвечай
   на языке этого промпта» — в смешанном составе модели иначе отвечают вразнобой, и сведённый
   вердикт получается двуязычным.
2. **Все** дополнительные пожелания пользователя из запроса — дословно
   («дополнительно ищи кривые буквы», «смотри только на конкурентность»).
   Пожелания пользователя приоритетнее стандартного фокуса и могут его сужать или заменять.
3. Указание проверять локально: «сверяйся с локальным CLI/кодом; веб-поиск — только если локально
   проверить нельзя» — иначе модель уходит гуглить документацию и прогон растягивается в разы.
4. Проверка фактов: «если автор утверждает факт о коде, схеме или конфигурации — проверь его
   и отметь неверные», плюс блок `ПРОВЕРКА ФАКТОВ` в формате ответа: документ и пересказ легко
   воспроизводят то, чего в системе нет.
5. Право спросить заказчика: «блок `ВОПРОСЫ ЗАКАЗЧИКУ` — 0–3 пункта, не обязателен».
   Участник изолирован от пользователя и недостающее достраивает догадкой; фильтр — `references/chair.md`.

Промпт от ~40 строк пиши файлом и подавай перенаправлением ввода — иначе при внешнем сбое
(обновление CLI, таймаут) heredoc придётся набирать заново, а слегка другой текст делает
результаты несравнимыми:

- codex: `zsh ~/.claude/skills/consilium/scripts/codex-run.sh <слаг> <effort> <репо> <prompt.md> <итог.md> [session-id]`
- cursor: `zsh ~/.claude/skills/consilium/scripts/cursor-run.sh <слаг> <воркспейс> <prompt.md> <итог.md> <chatId>`

Обёртки ставят `-s read-only`, проверяют, что out-файл уникален, кладут stdout целиком
в `<итог>.stdout` и печатают `session id:`. Собственный пайп к codex не приделывай:
`| tail`/`| grep` обрезают баннер, и id участника теряется вместе с ним.
Ручная сборка команды нужна только там, где скрипт не подходит: `review` со скоуп-флагами
и разовые пробы CLI.

## Каркас вызова

Типовой запуск участника уже собран: `scripts/codex-run.sh` (и `scripts/cursor-run.sh` для grok) —
см. «Промпт для участников». Ниже — из чего он состоит и что менять в нестандартных случаях.

Канонический каркас (строго до сабкоманды обязательны только `-C`/`-s`):

```
codex exec -C <корень репо> -s read-only $MODEL [review] -o <scratchpad>/<уникальный файл>.md …
```

- Строго parent — только `-C`/`-s` (после `review`/`resume` — exit 2). `-m`/`-c`/`-o` есть
  и у сабкоманд; канон: `-m`/`-c` до сабкоманды, `-o` для `review` — после неё
  (parent-`-o` проверен и работает для `exec` и `resume`, для пути `review` — не подтверждён).
- Без явного `-s read-only` санбокс берётся из конфига пользователя — read-only не гарантирован.
- `<scratchpad>` — плейсхолдер: подставь **абсолютный** путь scratchpad-каталога сессии
  (нет такого — создай через `mktemp -d`). Имя файла уникально на каждый прогон и ретрай,
  иначе рискуешь прочитать итог прошлого запуска.
- Делимитер heredoc генерируй уникальным на каждый вызов (например `CX_<случайный суффикс>`)
  и убедись, что такой строки нет в промпте: пожелания пользователя вставляются дословно.
- stdin в Bash tool — pipe: промпт аргументом → закрывай stdin через `</dev/null`, иначе codex ждёт EOF.

## Код-ревью

Скоуп-флаги и позиционный промпт у `review` **несовместимы** (`cannot be used with '[PROMPT]'`). Две формы:

- Чистое ревью без фокуса → скоуп-флаг: `review --uncommitted` | `review --base <ветка>` | `review --commit <sha>`.
- Ревью с фокусом/контекстом → custom-промпт через heredoc (не через кавычки: в пожеланиях
  пользователя могут быть `"` и `$()` — инъекция в shell). Скоуп задавай текстом и точно:
  заранее вычисли merge-base SHA, явно скажи, включать ли незакоммиченное:

```bash
codex exec -C /path/to/repo -s read-only \
  -m gpt-5.6-sol -c model_reasoning_effort=high \
  review -o "<scratchpad>/codex-review-1.md" - <<'CODEX_PROMPT'
Ты — код-ревьюер. Проревьюй изменения текущей ветки относительно merge-base abc1234 (origin/main).
Незакоммиченные изменения не рассматривай.
Контекст: TICKET-1234, рефакторинг ретраев в consumer.
Фокус: корректность, конкурентность, обработка ошибок. Стиль не комментируй.
Формат каждой находки: серьёзность (блокер/риск/замечание), file:line, суть в 1-2 предложениях, предлагаемый фикс.
CODEX_PROMPT
```

- Скоуп не назван → при незакоммиченных изменениях ревьюй рабочее дерево, при чистом — против
  дефолтной ветки (проверь, какая существует; несколько remote или нет main/master → спроси пользователя).
- Ревью чужого MR требует материализовать его состояние (codex видит только локальный репозиторий).
  Способ выбирает пользователь — спроси, молча не создавай worktree и не двигай ветки:
  1. **fetch-only** (дефолт, когда спросить нельзя): рабочее дерево не трогается. Fetch — один
     раз до старта участников и не повторять до конца совещания, в уникальные session-refs
     (не в `origin/*`: параллельный fetch соседей не сдвинет вход):
     `S=$(uuidgen); echo "SESSION_REF=$S"; git fetch --no-tags origin "+refs/heads/<дефолтная ветка>:refs/codex-review/$S/base" "+refs/merge-requests/<iid>/head:refs/codex-review/$S/head"`
     — `echo` обязателен: дальше значение используется только литералом, между вызовами
     Bash tool переменные не сохраняются.
     (ветка из fork → второй fetch с URL fork'а). Один раз вычисли BASE/HEAD/merge-base
     (`git rev-parse`, `git merge-base`) и передай в промпт: «рассматривай только diff
     `<MB>..<HEAD>`, контекст файлов читай из `<HEAD>` через git, рабочее дерево игнорируй».
     Файлы на диске — не MR, пометь ограничение в вердикте.
     После всех resume/совещания: `git update-ref -d` обоих session-refs.
  2. **inline checkout**: точный контекст, но двигает рабочее дерево — только при чистом
     и с возвратом исходной ветки после ревью.
  3. **отдельный worktree**: точный контекст + изоляция. Все вызовы этого ревью — включая
     resume, раунды и совещание — идут с `-C <путь worktree>`: резюмированной сессии нужен
     ревьюируемый код на диске (сам id от cwd не зависит — resume по UUID работает из любого
     `-C`, к cwd привязан только `--last`), поэтому удаляй worktree только после конца
     совещания и всех уточнений:
     `git worktree remove <путь>` (read-only ревью оставляет дерево чистым, remove пройдёт
     без --force; не прошёл → что-то писало в дерево, разберись, не форси).
     Осиротевшие — `git worktree list` + `prune`.
- В промпт: контекст задачи (тикет, что и зачем менялось) плюс пожелания пользователя — codex их сам не знает.

## Ревью документов (архитектура, планы, спеки)

`review` работает только с git-диффами. Для документов используй `codex exec`, промпт — через heredoc (stdin занят промптом, `</dev/null` не нужен):

```bash
codex exec -m gpt-5.6-sol -c model_reasoning_effort=high -s read-only \
  -C /path/to/repo \
  -o "<scratchpad>/codex-doc-review-1.md" - <<'EOF'
Ты — архитектурный ревьюер. Прочитай docs/plans/ticket-1234-plan.md.
Дай структурированное ревью:
1. Блокеры: противоречия, дыры в логике, невыполнимые шаги.
2. Риски: отказы, миграции, нагрузка, обратная совместимость.
3. Упущено: альтернативы, edge cases, наблюдаемость.
4. Вопросы автору.
Сверяйся с реальным кодом в репозитории, не оценивай документ в вакууме.
EOF
```

- Cwd (`-C`) вне git-репозитория → добавь `--skip-git-repo-check` (важно расположение cwd, не документа).
- В промпте всегда: путь к документу, роль ревьюера, структура ответа, указание сверяться с кодом, пожелания пользователя.

## Мультимодельные режимы

Что стоит за формулировкой пользователя — и во что это обходится. Цена в вызовах: N — число
участников (дефолт 3), время — календарное, при параллельном запуске.

| Просят | Что запускается | Цена |
|---|---|---|
| «проревьюй через codex/opus/grok» | один участник, без раундов | 1 вызов, 5–15 мин |
| «консилиум», «второе мнение» | N участников параллельно + синтез (дефолт sol + 5.5 + opus, high) | N вызовов, 10–15 мин |
| «консилиум с xhigh», «добавь grok» | тот же цикл, другой состав или effort | N вызовов |
| «полный консилиум», «пусть проверят друг друга», «в K раундов» | + раунды верификации: свежие сессии голосуют по анонимным находкам | ×K вызовов |
| «пусть обсудят», «до консенсуса», «дебаты» | + совещание: живые сессии, адресные вопросы, дефолт 3 итерации | + до 3×N |
| «с адвокатом дьявола», «пусть кто-то будет против» | + атака на консенсус кросс-вендорной моделью; число адвокатов — параметр | +1 и больше |
| «с премортемом» | + сценарии провала решения (только для документов и архитектуры) | +1 и больше |
| «дизайн-консилиум», «пусть предложат решения», «как лучше сделать X» | этапы 0–5: требования → предложения → перекрёстное ревью → выбор → итерации → финал | 2N + итерации, часы |
| «дизайн-консилиум в K раундов» | то же, K итераций доработки с чередованием «доработка → атака» | + K×N |

Комбинируются свободно («консилиум с xhigh, с адвокатом и премортемом»), порядок исполнения
фиксирован — он задан в `deliberation.md`. Что не названо явно, определяется по глаголу запроса
и уточняется вопросом (`council.md`, «Выбор типа перед запуском»).

Запрос консилиума, совещания, раундов, адвоката дьявола, премортема или вопроса участнику —
**сначала прочитай** нужный reference (в контекст по умолчанию они не загружены):

- `references/council.md` — консилиум: интерактивный выбор типа (AskUserQuestion), состав
  и дефолты (sol + 5.5 + opus), клод- и cursor-участники (opus/grok), адвокат дьявола.
- `references/deliberation.md` — раунды верификации, совещание до консенсуса, вопросы
  пользователя участникам, премортем и эскалация.
- `references/design.md` — дизайн-совет: участники предлагают решения задачи, перекрёстно
  ревьюят, выбирают лучшее и итеративно улучшают («пусть предложат решения», «как лучше сделать X»).
- `references/chair.md` — роль председателя: сбор требований до запуска участников, проверка
  фактов по коду, вопросы заказчику, сверка с исходной задачей, лог и тайминги.
- `references/finalization.md` — закрытие цикла: кворум, ревью итогового документа, пакет передачи.

Что читать под режим — не «всё подряд»: `chair.md` и `finalization.md` нужны там, где есть
требования заказчика и итоговый документ, а не в каждом цикле с раундами.

| Режим | Дополнительно к рецептам хаба |
|---|---|
| Код-ревью, в том числе в K раундов и с совещанием | `deliberation.md`; лог — по `council.md`. Этап 0 и кворум не применяются: нет ни автора решения, ни итогового документа |
| Ревью архитектурного решения, плана, спеки — даже одним участником | `chair.md` (этап 0 до запуска участников). Результат такого ревью — вердикт, а не новый документ: кворум и `finalization.md` не нужны. Они включаются, только если по итогам ты сам пишешь документ заказчику |
| Дизайн-совет | `design.md` + `chair.md` до старта + `finalization.md` в финале |

Также читай `council.md` при одиночном ревью не-codex участником («ревью через opus/grok») —
запуск клод- и cursor-участников описан только там. Вопросы участникам Claude/Grok
и смешанное совещание требуют обоих references.
Не запускай мультимодельный режим по памяти: механика вендоров различается в деталях
(session id у codex, agentId у клода, chatId у grok), и все детали — там.

## Обработка результата

Пункты 1, 3 и 5 — про codex, пункт 2 — про клод-сабагентов; артефакты и критерии сбоя
остальных вендоров — таблица в `references/council.md`.

1. Сначала проверь exit code и что файл `-o` существует и непустой, потом читай его.
   Stdout не используй как содержательный результат (баннер, хуки, прогресс) — бери из него
   только строку `session id:`; итог всегда из `-o`.
2. **Артефакт участника, существующий только в контексте, не существует.** Результат
   клод-сабагента возвращается лишь в контекст оркестратора — сохраняй его в файл scratchpad
   **в том же ходе**, в котором получил, по той же схеме имён, что и `-o` у codex. Длинный цикл
   почти гарантированно переживает компактификацию, а голоса и вердикты нужны в самом конце.
   Результат всё же потерян → последнее сообщение с `type: assistant` и непустым текстовым блоком
   в `~/.claude/projects/<слаг проекта>/<uuid текущей сессии>/subagents/agent-<agentId>.jsonl`.
   Uuid сессии в пути обязателен (без него каталога не существует); не знаешь его —
   `find ~/.claude/projects/<слаг проекта> -name 'agent-<agentId>.jsonl'`. Текст последнего ответа:
   `python3 -c "import json,sys; rs=[json.loads(l) for l in open(sys.argv[1]) if '\"assistant\"' in l]; ts=[t for r in rs for b in r.get('message',{}).get('content',[]) if b.get('type')=='text' and (t:=b['text'].strip())]; print(ts[-1])" <файл>`
   (берётся последний **непустой текстовый** блок: последняя assistant-запись может состоять
   из одного tool_use, и наивный вариант вернёт пустоту).
3. Ревью идёт минуты: `timeout: 600000` или `run_in_background` (параметры Bash tool, не codex).
   Если Bash tool умеет отключать внешнюю песочницу (`dangerouslyDisableSandbox: true`) —
   отключай: вложенный санбокс ломает tool-host codex («timed out negotiating with the
   code-mode host»); чтение-только гарантирует его собственный `-s read-only`.
   Истёкший timeout — инфраструктурный сбой, не падение модели: перезапусти прогон
   через `run_in_background`, повторный полный раунд не нужен.
   Ориентир: участник на xhigh — 5–15 минут на этап, дизайн-цикл с итерациями — часы; сообщай
   пользователю календарное время, а не число вызовов. Цикл растёт сам: на 15 запусках или двух
   часах — обязательная остановка с отчётом и выбором пользователя (чекпоинт по объёму,
   `references/chair.md`). Прогон со статусом «остановлена» и пустым
   файлом — инфраструктурный сбой: перезапускай, а не пересказывай как позицию участника.
4. Перескажи находки пользователю со своей оценкой: с чем согласен, с чем нет и почему.
   Критичные утверждения проверяй сам (пробы парсера, чтение кода) — не транслируй вслепую.
   Фундаментальные блокеры в основе решения → вердикт «не согласовано — вернуться после
   правок» (правила эскалации — references/deliberation.md).
5. Уточняющий вопрос → resume строго по session id (строка `session id:` в шапке вывода —
   единственное, что бери из stdout). Каркас тот же, что у обычного вызова, — санбокс и `-o`
   не наследуются молча, задавай явно; вопрос только через heredoc (аргументная форма — инъекция):
   `codex exec -C <репо> -s read-only -m <модель прогона> -c model_reasoning_effort=<его effort> -o <уникальный файл> resume <id> - <<'EOF' … EOF`.
   `--last` не используй: фильтруется по cwd и гонится с параллельными сессиями.
6. Ничего не исправляй по находкам без явной просьбы.
7. Пользователь отменил или сменил запрос → останови фоновые прогоны (TaskStop по их task id)
   или дождись завершения; затем убери worktree/session-refs и пометь результат неполным.
8. В конце цикла проверь осиротевшие процессы: `ps -ax | grep -E 'codex exec|cursor-agent'` —
   интерактивные команды без TTY (Ink) могут висеть вечно даже после ошибки. Останавливай
   **только свои**: фоновые прогоны — по их task id (TaskStop), остальные опознавай в выдаче `ps`
   по аргументам **своего** запуска — у codex это `-C <путь>` и имя out-файла, у cursor-agent —
   `--workspace <путь>` и `--resume <свой chatId>` (редирект вывода в командной строке не виден,
   поэтому опознавай по chatId). PID Bash tool не возвращает, поэтому «добить всё по имени
   процесса» нельзя — в выдаче бывают прогоны соседних сессий пользователя.
   Пробы CLI (свои и в промптах участникам) ограничивай таймаутом: в Bash tool — параметром
   `timeout` самого вызова; команды `timeout(1)` на macOS нет — внешним timeout только если
   он установлен.
   Значения из `$(...)` (session-refs, chatId) не живут между вызовами Bash tool — выведи
   и подставляй в следующие команды литералом. Многошаговые запуски оформляй скриптом
   в scratchpad и вызывай `zsh <файл>`: PreToolUse-хуки среды (свои у Claude Code, codex
   и cursor) инспектируют инлайновую команду и могут её отклонить — содержимое скрипта они
   не разбирают.
   Список длинных находок для раундов/совещания клади файлом и передавай путь — heredoc
   с десятками находок раздувает команду и растит риск коллизии делимитера. Codex в read-only
   читает и вне `-C` (проверено пробой), воркспейс grok — нет: в составе с grok вход кладётся
   внутрь репо, одним путём для всех участников (`references/council.md`).

## Common mistakes

| Ошибка | Как правильно |
|---|---|
| `-m sol-high` (слитный слаг) | `-m gpt-5.6-sol -c model_reasoning_effort=high` |
| Скоуп-флаг + позиционный промпт у `review` | Несовместимы: либо флаг без промпта, либо custom-промпт со скоупом текстом |
| `-C`/`-s` после слова `review` | Это опции `exec` — ставь до сабкоманды |
| Вызов без `-s read-only` | Санбокс возьмётся из конфига, возможно workspace-write |
| Промпт аргументом без `</dev/null` | Piped stdin → codex ждёт EOF и не стартует |
| Интерактивный `codex` без `exec`; `cursor-agent ls` и прочие TUI в Bash | Блокируют/виснут без TTY (Ink). Только неинтерактивные формы, пробы — с timeout |
| Вставка диффа в промпт | Codex сам читает репо |
| `--approve-for-me`, `--dangerously-bypass-*`, `-s workspace-write`, `-s danger-full-access` | Запрещены: ревью только на чтение |
| Ревью без контекста задачи | Тикет, цель изменений и хотелки пользователя — в промпт |
| Мультимодельный режим по памяти | Сначала прочитай `references/council.md` / `references/deliberation.md` / `references/design.md` |
| Результат клод-сабагента остался только в контексте | Сохраняй в файл scratchpad в том же ходе: компактификация съест голос участника |
| Проектирование до сбора требований | Этап 0 в `references/chair.md`: числа спрашиваются у заказчика до запуска участников |
| Цикл закрыт молчаливым «все согласны» | Кворум и ревью итогового документа — `references/finalization.md` |
| Длинный промпт heredoc'ом прямо в команде | От ~40 строк — файл в scratchpad, запуск скриптом: сбой CLI иначе стоит перенабора |
| Чужое утверждение о коде пересказано без проверки | Критичные факты председатель проверяет сам, с указанием file:line |
